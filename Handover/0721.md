## 2. ★venvへの移行(今日地味に重要)★

### 発覚の経緯
Google系ライブラリをインストールする過程で、Antigravity(エディタ)が「グローバル環境に入れてるが仮想環境を作るか?」と提案してきた。これまで`claude-agent-sdk`や`requests`もずっとグローバルに入れてきていたため、ここで初めてプロジェクト専用の`.venv`を作ることになった。

### ★注意点として残った教訓★
venvを作っても、**ターミナルで明示的に有効化(activate)しないと、コマンドはグローバル環境を見続ける**。

```powershell
.\.venv\Scripts\Activate.ps1
```

有効化に成功すると、プロンプトの先頭に`(.venv)`が付く。これが出てない状態でのコマンド実行は、全部グローバル環境に対して行われてしまう。

### 実際に起きた事故(小さいが2回)
1. 最初に`google-auth-oauthlib`等をインストールした時、venv作成前だったため**グローバルに入ってしまった**(実害なし、後でvenv内に入れ直した)
2. SDKの調査で`import claude_agent_sdk`のパスを確認した際も、**`(.venv)`表示が無いターミナルで実行**していたため、グローバル版のパスが返ってきた。慌てず`sys.executable`で現在の実行環境を確認する癖を挟んで気づけた

### ★確認の型★
迷ったらこの2行で「今どの環境で動いてるか」を確定させる:

```powershell
python -c "import sys; print(sys.executable)"
```

`.venv\Scripts\python.exe`が出ればvenv、それ以外ならグローバル。**プロンプトの`(.venv)`表示だけに頼らず、実行結果そのもので確認する**のが安全。

## 3. Google Cloud Console 設定(OAuth2の下準備)

Google Calendar APIはAsanaと違い、隼個人の予定という機微な情報を扱うため**OAuth2**が必須。手順は以下の4段階:

1. **Cloud Consoleでプロジェクト作成**(`FALCON`という名前で)
2. **Calendar APIの有効化**(「APIとサービス」→「ライブラリ」から検索して有効化)
3. **OAuth同意画面の設定**
   - User Typeは「外部」(個人アカウントなので)
   - アプリ名・サポートメールのみ必須、他は空欄でOK
   - スコープはこの画面では設定不要(コード側で指定する)
   - ★重要★ テストユーザーに隼自身のGmailを登録。「アプリを公開」しない限りテストモードのままで、登録したユーザーしかログインできない(他人が使えない = むしろ安全)
4. **OAuthクライアントIDの作成**
   - アプリケーションの種類は**「デスクトップアプリ」**を選択(FALCONはPC上で直接動くスクリプトであり、Webアプリではないため)
   - 作成後、JSON形式でダウンロード

### ★「将来iOSでも動かしたい」への回答★
隼から「最終的にはスマホでも動かしたいのに、今デスクトップアプリでいいのか」という指摘があった。結論は**問題ない**。

- OAuthのクライアント種別は「今どこで認証が起きるか」を表すもので、「将来どこで動くか」を縛るものではない
- サーバー+PWA化した際は、認証はサーバー側で一元管理する形に変わる(隼のiPhoneが直接Googleと喋るわけではない)。その時点でクライアント種別を「ウェブアプリケーション」に作り直すことになるが、それはロードマップの3番目に来た時の話
- 「推測で語らず現物を確認する」の精神で、**今作ってるのはまだPC単体のコンソール版**であることを踏まえ、今日決めるのは「今のPC版のCalendar連携」だけに絞った

### ファイルの配置
ダウンロードしたJSONは `config/google_client_secret.json` にリネームして配置。`.gitignore`にも追加:

```
# Google OAuth
config/google_client_secret.json
config/google_token.json
```

`google_token.json`はまだ存在しないファイルだが、初回認証成功時に自動生成されるため先に予約した。

## 5. `core/tools/google_auth.py`(認証モジュール)

```python
import os
from google.auth.transport.requests import Request
from google.oauth2.credentials import Credentials
from google_auth_oauthlib.flow import InstalledAppFlow

SCOPES = ["https://www.googleapis.com/auth/calendar"]

CONFIG_DIR = os.path.join(os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__)))), "config")
CLIENT_SECRET_PATH = os.path.join(CONFIG_DIR, "google_client_secret.json")
TOKEN_PATH = os.path.join(CONFIG_DIR, "google_token.json")

def get_calendar_credentials() -> Credentials:
    creds = None
    if os.path.exists(TOKEN_PATH):
        creds = Credentials.from_authorized_user_file(TOKEN_PATH, SCOPES)

    if not creds or not creds.valid:
        if creds and creds.expired and creds.refresh_token:
            creds.refresh(Request())
        else:
            flow = InstalledAppFlow.from_client_secrets_file(CLIENT_SECRET_PATH, SCOPES)
            creds = flow.run_local_server(port=0)

        with open(TOKEN_PATH, "w", encoding="utf-8") as f:
            f.write(creds.to_json())

    return creds
```

### 設計のポイント
- **優先順位が明確**: ①既存トークンを読む → ②期限切れなら`refresh_token`で自動更新(ブラウザ不要) → ③どちらも無理なら初回のみブラウザで同意フロー
- **`flow.run_local_server(port=0)`** がデスクトップアプリ認証の心臓部。PC上に一時的なローカルサーバーを立て、ブラウザでの許可結果を受け取る。`port=0`で空きポートを自動選択
- **`TOKEN_PATH`は固定値でコード側が決めている**ため、`memo.py`の`read_memo`のようなパストラバーサル対策は不要(外部入力の影響を受けないため、警戒すべき箇所が違う)

## 6. `core/tools/calendar.py`(Calendar操作モジュール)

```python
from datetime import datetime, timedelta
from googleapiclient.discovery import build

from core.tools.google_auth import get_calendar_credentials


def get_calendar_service():
    creds = get_calendar_credentials()
    return build("calendar", "v3", credentials=creds)


def list_events(days: int = 7, max_results: int = 10) -> dict:
    service = get_calendar_service()
    now = datetime.utcnow()
    time_min = now.isoformat() + "Z"
    time_max = (now + timedelta(days=days)).isoformat() + "Z"

    try:
        result = service.events().list(
            calendarId="primary",
            timeMin=time_min,
            timeMax=time_max,
            maxResults=max_results,
            singleEvents=True,
            orderBy="startTime",
        ).execute()
    except Exception as e:
        return {"error": f"予定の取得に失敗しました: {e}"}

    events = result.get("items", [])
    formatted = []
    for event in events:
        start = event["start"].get("dateTime", event["start"].get("date"))
        formatted.append({
            "summary": event.get("summary", "(タイトルなし)"),
            "start": start,
            "id": event.get("id"),
        })

    return {"events": formatted}


def create_event(summary: str, start: str, end: str, description: str = "") -> dict:
    service = get_calendar_service()

    event_body = {
        "summary": summary,
        "description": description,
        "start": {"dateTime": start, "timeZone": "Asia/Tokyo"},
        "end": {"dateTime": end, "timeZone": "Asia/Tokyo"},
    }

    try:
        result = service.events().insert(calendarId="primary", body=event_body).execute()
    except Exception as e:
        return {"error": f"予定の作成に失敗しました: {e}"}

    return {
        "id": result.get("id"),
        "summary": result.get("summary"),
        "start": result.get("start", {}).get("dateTime"),
        "link": result.get("htmlLink"),
    }
```

### 設計のポイント
- **`"timeZone": "Asia/Tokyo"`を明示** … Google Calendar APIはタイムゾーンを明示しないと事故る。「14時」のつもりが9時間ズレて登録される危険を、明示指定で防いでいる。`weather.py`で「areas[0]にフォールバックしない」とやったのと同じ精神で、曖昧なまま渡さない
- **`event["start"].get("dateTime", event["start"].get("date"))`** … 予定には「時刻あり」と「終日予定」の2パターンがあるため、フォールバックで両対応。ただしこれは「正規の別パターンの吸収」であり、`weather.py`の「間違った場所を返す」危険とは性質が異なる
- **`start`/`end`はISO 8601形式の文字列で受け取る**設計。自然文の解釈(「明日の14時」など)はここでパースせず、FALCON(Claude)側の仕事とする。`search_memos`と同じ「賢さは呼ぶ側に任せる」方針を踏襲

## 8. ★バグ1: `@tool`定義の位置ミス(現物確認で発覚)★

### 経緯
隼が反映したコードで、`list_events_tool` / `create_event_tool` の`@tool`定義が、ファイルの**一番下**(`if __name__ == "__main__":`より後ろ)に置かれていた。一方`falcon_tools = create_sdk_mcp_server(tools=[..., list_events_tool, create_event_tool])`はそれより**上**にあった。

### 問題
Pythonはファイルを上から順に実行するため、`falcon_tools`を組み立てる時点でまだ`list_events_tool`という名前が定義されておらず、実行時に`NameError`で落ちる状態だった。

### 教訓
`weather_tool`内で`get_weather`のimportが消えても起動時にはエラーにならない(呼ばれるまでチェックされない)話と混同しやすいが、**今回は関数の中身ではなく、モジュールの一番外側でその場評価される`falcon_tools = create_sdk_mcp_server(...)`が、まだ存在しない名前を今すぐ参照してしまう話**で、別種の順序問題。

### 対処
`list_events_tool` / `create_event_tool` の定義を、`read_memo_tool`の直後・`falcon_tools`定義より前に移動。

## 9. ★バグ2: `ask_claude`の二重定義(現物確認で発覚)★

### 経緯
日付問題の調査で、`ask_claude`に`[DEBUG]`のprint文を仕込んだテスト版を書いた後、日付を付ける本番版の`ask_claude`をファイル冒頭に追加した。しかし**調査用の古い`ask_claude`(DEBUG付き・日付無し)を消し忘れ**、ファイル内に同名の関数が2つ存在する状態になっていた。

### 問題
Pythonは同名の関数が複数あると、**後に定義された方で上書き**される。ファイル下部にあった調査用の古い版が有効になり、せっかく書いた日付付きの新しい版が完全に無視されていた。

### 対処
ファイル下部の古い`ask_claude`(DEBUG付き)を削除。冒頭の日付付きバージョンのみを残した。

### 教訓
`memo.py`で`search_memos`を意図的に3回定義し直した時と構造は同じだが、今回は**意図せず古いコードが残ったパターン**。一時的なデバッグ用コードを仕込んだら、役目が終わったら忘れずに消すこと。

## 10. 日付問題の調査と対処(B案採用)

### 発端
`create_event`のテストで「明日の15時から16時」と指示したところ、FALCONは正しく7/21・15:00〜16:00で予定を作成した。しかし**なぜ正しい日付を認識できたのか根拠不明**だったため、「たまたま当たった」可能性を排除できず調査した。

### 調査の流れ(現物確認の実践)
1. `ask_claude`に`[DEBUG]`出力を仕込み、`SystemMessage`や`AssistantMessage`の中身を確認 → 日付情報らしきものは見当たらず、`ToolUseBlock`も無い(ツール経由で調べたわけではない)
2. `claude_agent_sdk`のソースコードを`Select-String`でキーワード検索(`datetime|today|current date|<env>|working_directory`) → ヒットしたのは全部**セッション記録用のタイムスタンプ**で、Claudeへの入力に日付を注入する仕組みは見つからず
3. 結論: **`claude_agent_sdk`(Pythonラッパー)自体には日付を渡す仕組みが無い**。渡してるとしたら、SDKが起動する`@anthropic-ai/claude-code`(Node.js製CLI本体)側の可能性があるが、そこは未調査

### ★判断: 根本原因の深掘りより実利を優先(B案)★
CLI側の仕組みを追う(A案)か、原因究明を諦めて確実な対処だけ打つ(B案)かを検討し、**B案を採用**。`create_event`で日付がズレる実害の大きさに対し、対処自体は数行で済むため、B案だけで安全性は十分確保できると判断。

### 実装
`ask_claude`関数内で、ユーザーメッセージの前に毎回「今日の日付」を付加する:

```python
async def ask_claude(client: ClaudeSDKClient, user_message: str) -> str:
    today_str = datetime.now().strftime("%Y年%m月%d日(%a)")
    message_with_date = f"[今日の日付: {today_str}]\n{user_message}"

    await client.query(message_with_date)

    answer = ""
    async for message in client.receive_response():
        if isinstance(message, ResultMessage) and message.result:
            answer = message.result
    return answer
```

### なぜ`SYSTEM_PROMPT`ではなく`ask_claude`に書いたか
`SYSTEM_PROMPT`は`FALCON_OPTIONS`内で1回だけ設定される固定文字列で、セッション開始時の日付で固まってしまい翌日には更新されない。`ask_claude`は毎ターン呼ばれるため、ここに仕込めば常に最新の日付が渡る。

### 検証結果
`python core\brain.py`(`_test()`で「今日は何月何日?」を質問)→「2026年7月21日(火)です。」日付・曜日とも正確。`[DEBUG]`出力も出ず、バグ2の修正も確認できた。

### 経緯

### 設計
- 保存形式は`memo.py`のような1件1ファイルではなく、**JSON1ファイル**(`tasks/tasks.json`)。タスクは一覧性・状態管理(未完了/完了)・並び替えが要る性質のため、全件を1回の読み込みで扱えるJSONの方が適していると判断
- 1件のタスクは `id` / `title` / `status`(`"todo"` or `"done"`) / `due`(任意) / `created` を持つ
- **期限(`due`)は任意**にすると決定。必須にすると「期限はいつですか?」と毎回確認する手間が増えるため、期限の無いタスクもサッと追加できる方を優先

### `core/tools/tasks.py`

```python
import json
import os
from datetime import datetime

TASKS_DIR = os.path.join(
    os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__)))),
    "tasks",
)
TASKS_FILE = os.path.join(TASKS_DIR, "tasks.json")


def _load_tasks() -> list:
    if not os.path.exists(TASKS_FILE):
        return []
    with open(TASKS_FILE, "r", encoding="utf-8") as f:
        return json.load(f)


def _save_tasks(tasks: list) -> None:
    os.makedirs(TASKS_DIR, exist_ok=True)
    with open(TASKS_FILE, "w", encoding="utf-8") as f:
        json.dump(tasks, f, ensure_ascii=False, indent=2)


def add_task(title: str, due: str = None) -> dict:
    tasks = _load_tasks()
    existing_ids = [int(t["id"]) for t in tasks] if tasks else []
    new_id = str(max(existing_ids) + 1) if existing_ids else "1"

    new_task = {
        "id": new_id,
        "title": title,
        "status": "todo",
        "due": due,
        "created": datetime.now().strftime("%Y-%m-%d %H:%M:%S"),
    }

    tasks.append(new_task)
    _save_tasks(tasks)
    return {"task": new_task}


def list_tasks(include_done: bool = False) -> dict:
    tasks = _load_tasks()

    if not include_done:
        tasks = [t for t in tasks if t["status"] == "todo"]

    def sort_key(t):
        return (t["due"] is None, t["due"])

    tasks.sort(key=sort_key)
    return {"tasks": tasks}


def complete_task(task_id: str) -> dict:
    tasks = _load_tasks()
    for t in tasks:
        if t["id"] == task_id:
            t["status"] = "done"
            _save_tasks(tasks)
            return {"task": t}
    return {"error": f"ID {task_id} のタスクが見つかりませんでした。list_tasksで確認してください。"}


def delete_task(task_id: str) -> dict:
    tasks = _load_tasks()
    remaining = [t for t in tasks if t["id"] != task_id]

    if len(remaining) == len(tasks):
        return {"error": f"ID {task_id} のタスクが見つかりませんでした。list_tasksで確認してください。"}

    _save_tasks(remaining)
    return {"deleted_id": task_id}
```

### 設計のポイント
- **IDは連番の文字列**(`memo.py`のファイル名ベースの一意性とは違うアプローチ)。隼が「2番完了して」と口頭で指示しやすいことを優先し、UUID等の長い識別子は避けた
- **`list_tasks`の並び替え** … `sort_key`で`(due is None, due)`のタプルを返し、期限があるものを近い順に先頭へ、期限が無いものは後ろに回す。`YYYY-MM-DD`形式の文字列比較がそのまま日付順と一致することを利用している
- **`complete_task`/`delete_task`は「見つからなかった場合」を明示的にエラーとして返す** … `memo.py`の`read_memo`と同じ、正常系・異常系どちらも同じ形(dict)で返す設計
- **`delete_task`は「削除対象以外」でリストを作り直す方式** … ループ中に同じリストを直接削ると要素がズレる事故を避けるため

### `core/brain.py`への統合
- import: `from core.tools.tasks import add_task, list_tasks, complete_task, delete_task`
- `@tool`定義4つ(`add_task_tool` / `list_tasks_tool` / `complete_task_tool` / `delete_task_tool`)を追加
- `delete_task`のツール説明文に「取り消せないので実行前に確認すること」と明記(SYSTEM_PROMPTの一般ルールに加えた二重の安全弁)
- `falcon_tools`・`allowed_tools`にそれぞれ追加。ツール数は7個 → **11個**に

## 17. サーバー+PWA化(自宅PC構成・MVP)

### 経緯
タスク管理完成後、最終目標である「サーバー+PWA化」に着手。ロードマップの中でも一番大きなテーマだが、まずは「自宅Wi-Fi経由でスマホから会話できる」という最小構成(MVP)を目指した。

### 方針決定: 自宅PCで動かす
サーバーの置き場所として、自宅PC(無料・家の中/VPN経由でのみ利用)か、クラウド(有料・外出先からもどこでも利用)かを検討し、**自宅PC**を選択。まずステップ1(家の中からのアクセス)を固め、外出先からのアクセス(VPN経由)はステップ2として後回しにする方針にした。

### 電源運用の方針
「画面は真っ黒にしたいが、FALCONは動き続けてほしい」という要望に対し、**「ディスプレイの電源を切る」と「PCのスリープ」は別物**であることを整理:
- ディスプレイの電源を切る … CPU・メモリは動き続けるため、サーバープロセスへの影響なし。これは自由に設定してよい
- PCのスリープ … サーバープロセスごと停止するため、**無効化が必須**
- 合わせて、**ネットワークアダプタの節電設定はオフにする必要がある**(省電力設定でLAN/Wi-Fiが眠ると、外部からのアクセスに気づかなくなる)。今回は方針決定のみで、実際の設定変更はまだ行っていない

### Wake-on-LANについて(調査のみ、実装は保留)
外出先からPCの電源そのものを入れる仕組み。BIOS/UEFIとWindows側のネットワークアダプタ設定、両方で「Magic Packetによる起動」を有効にする必要がある。家の外からパケットを届ける方法は、ポート開放(セキュリティ面で気を使う)かVPN経由(自宅LANの中にいる扱いになるため安全)の2択で、**VPN導入とセットで行うのが自然**という結論になった。今回は実装せず、次回のVPN導入時に合わせて着手する。

### 技術選定
- **バックエンド: FastAPI** … `ClaudeSDKClient`が元々`async`で書かれているため、非同期処理をネイティブに扱えるFastAPIとの相性を優先して選定。Flaskは非同期処理に追加の工夫が要るため見送り
- **セッション設計: サーバー起動時に1回だけ`ClaudeSDKClient`を作り、使い回す** … `main.py`で「`async with`を`while`の外に置く」とやった設計を、「サーバーの生存期間全体」に拡張した形。リクエストごとに作り直すと、また会話の文脈が失われる(0717の教訓の再現)ため、この一択とした

### `server.py`(サーバー本体)

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI
from fastapi.staticfiles import StaticFiles
from fastapi.responses import FileResponse
from pydantic import BaseModel
from claude_agent_sdk import ClaudeSDKClient

from core.brain import FALCON_OPTIONS, ask_claude

falcon_client: ClaudeSDKClient | None = None
chat_history: list[dict] = []


@asynccontextmanager
async def lifespan(app: FastAPI):
    global falcon_client
    async with ClaudeSDKClient(options=FALCON_OPTIONS) as client:
        falcon_client = client
        yield
    falcon_client = None


app = FastAPI(lifespan=lifespan)
app.mount("/static", StaticFiles(directory="static"), name="static")


@app.get("/")
async def root():
    return FileResponse("static/index.html")


@app.get("/history")
async def get_history():
    return {"history": chat_history}


class ChatRequest(BaseModel):
    message: str


class ChatResponse(BaseModel):
    reply: str


@app.post("/chat", response_model=ChatResponse)
async def chat(request: ChatRequest) -> ChatResponse:
    if falcon_client is None:
        return ChatResponse(reply="FALCONが起動していません。少々お待ちください。")

    chat_history.append({"sender": "隼", "text": request.message})
    reply = await ask_claude(falcon_client, request.message)
    chat_history.append({"sender": "FALCON", "text": reply})

    return ChatResponse(reply=reply)
```

### 設計のポイント
- **`@asynccontextmanager`と`lifespan`** … `yield`より前が「サーバー起動時に1回だけ」、後が「サーバー終了時に1回だけ」実行される処理になる。`main.py`の`async with ... : while True: ...`の構造を、FastAPIの「リクエストを待ち受け続ける」という役割に置き換えた形
- **`falcon_client`をモジュールレベルの変数として持つ** … `lifespan`内で作った`client`を、他のエンドポイント関数からも参照できるようにするため。`global falcon_client`で書き換え可能にしている
- **`chat_history`も同様にモジュールレベルで保持** … 会話ログの実体をサーバー側の1箇所にまとめる設計。ブラウザ側(localStorage等)に持たせると、端末ごとに履歴がズレる問題が起きるため、「記憶の実体は常に1箇所」という`memo.py`以来の原則を踏襲
- **`app.mount("/static", ...)`とルート(`/`)でのHTML配信** … `static/`フォルダをそのまま配信しつつ、`/`にアクセスした際は`index.html`を直接返すようにして、隼が`http://IPアドレス:8000/`だけでアクセスできるようにした
- **`chat_history`も`ClaudeSDKClient`も、現状はメモリ上のみに存在** … サーバーを再起動すると両方ともリセットされる。ファイルへの永続化は今回のスコープに含めていない

### ★バグ: `app`の定義順序ミス(現物確認で発覚)★
隼が反映したコードで、`@app.get("/")`などの`app`を使うデコレータが、`app = FastAPI(lifespan=lifespan)`より**前**に書かれていた。`list_events_tool`の時と同種の「モジュールの一番外側で、まだ存在しない名前を参照してしまう」問題で、実行時に`NameError`になる状態だった。加えてimportもファイル内に分散していたため、`app = FastAPI(...)`を最初に使う箇所より前に配置し、importも全てファイル先頭に集約する形で修正した。

### `static/index.html`(チャット画面)
HTML・CSS・JavaScriptを1ファイルにまとめた構成。主な要素:

- **`<meta charset="UTF-8">`** … 文字化け対策として最優先で指定
- **`<link rel="manifest" href="/static/manifest.json">`** … PWAとしての設定ファイルと紐づける
- **`chat-log`(履歴表示)と`chat-form`(入力フォーム)** … `form`にしたのは、スマホでEnterキー相当の送信ができるようにするため

主なJavaScript関数:
- **`addMessage(sender, text)`** … 発言者に応じて`user`/`falcon`/`system`のCSSクラスを付け分け、吹き出しとして表示
- **`loadHistory()`** … ページ読み込み時に`/history`を叩き、サーバー側の会話ログを画面に復元する
- **`form`のsubmitイベント** … `/chat`にPOSTし、返事を表示。`try/catch`で通信エラーを捕捉、送信中は`submitButton.disabled = true`で二重送信を防止

### ★PowerShellの文字コード沼(今日一番時間を使った切り分け)★
`Invoke-RestMethod`/`Invoke-WebRequest`(PowerShellの`curl`エイリアス)で`/chat`を叩いた際、送信・受信どちらの側でも繰り返し文字化けが発生した。

1. リクエストの`-Body`に文字列を渡すと、PowerShellがシステムのデフォルト文字コードでエンコードして送信してしまう(`-ContentType`の指定だけでは実際の送信バイト列は変わらない)ことが判明 → `[System.Text.Encoding]::UTF8.GetBytes(...)`で明示的にUTF-8のバイト列に変換して送る対処を実施
2. それでも化けが直らなかったため、`Out-File`でレスポンスをファイルに書き出しエディタで直接確認する方式に切り替えたが、それも実行せず

## メモ
- `model="claude-sonnet-5"`は引き続き動作。SDKのdocstring例は`claude-sonnet-4-5`系のままで、想定より新しいモデル名を使っている点は変わらず頭の隅に
- venv化により、今後のライブラリ追加は必ず`(.venv)`表示のあるターミナルで行うこと
- Google Cloud Consoleの認証情報は「テストモード」。隼自身のGmailのみテストユーザー登録済みなので、他人がこのアプリ経由でログインすることはできない
- `Select-String`によるコードベース横断検索(grep相当)は、`inspect.getsource`より広範囲を素早く確認したい時に有効。今日の日付機構調査で有効性を確認できた
- PowerShellでの日本語まわりの検証は、コンソール表示に頼らず`requests`(Python)経由かブラウザ経由で行うこと。今日、複数回の切り分けの末に判明した教訓
- `chat_history`・`ClaudeSDKClient`の会話文脈は、いずれも現状メモリ上のみに存在し、サーバー再起動でリセットされる仕様
