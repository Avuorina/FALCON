## 1. `search_memos`: タイトル行を拾うバグの修正

### 原因

`memo.py`の保存形式は `# タイトル` → ヘッダー(作成日時・種別) → `---` → 本文、という構造になっている。だが`search_memos`の抜粋(snippet)抽出ロジックは、この`---`の境目を無視して`body`全体(タイトル行込み)を先頭から走査していた。

```python
# 修正前
snippet = ""
for line in body.splitlines():
    if terms[0].lower() in line.lower():
        snippet = line.strip()
        break
```

検索語がタイトルにも含まれている場合(例: タイトル「カレー好き」で「カレー」を検索)、1行目のタイトル行で即ヒットして`break`し、本文中の実際の文脈には辿り着かなかった。

### 対処

`body.partition("---")` でヘッダーと本文を分離し、スニペットの走査対象を本文側(`content`)だけに変更した。本文側に一致箇所が無い(タイトル等ヘッダーにしかヒットしていない)場合は、空文字を返さず「(タイトルにヒット。本文中に一致箇所なし)」と正直に返すようにした。

### 検証

- タイトルに検索語を含むメモ → 本文中の実際の文脈が正しくスニペットに出ることを確認
- タイトルにしか検索語が無いメモ → フォールバック文言が返ることを確認
- 既存の`__main__`テスト(カレー/天気/牛乳/存在しない語、パストラバーサル攻撃系6パターン)が全て通ることを確認(回帰無し)

## 2. `search_memos`の死んだ重複定義を削除

### 発覚の経緯

`memo.py`には`search_memos`という名前の関数が**4つ**定義されていた。Pythonは同名関数を後の定義で上書きするため、実際に動いていたのは最後(4つ目、`limit=5`版)だけ。上の3つ(`matched_lines`版・`snippet substring`版、および今回修正した4つ目より前にあった版)は一度も呼ばれていない死んだコードだった。

0721で踏んだ`ask_claude`の二重定義バグ(古いDEBUG版が消し忘れで生き残っていた件)と**構造的にまったく同じ地雷**が、たまたま実害無く埋まっていただけの状態。

### 対処

死んでいた2つの`search_memos`(`matched_lines`版・`snippet substring`版)を削除。生きている`limit=5`版(AND検索・今回スニペット修正済み)のみを残した。

### 検証

削除後も`import`が正常に通ること、`__main__`の一連のテストが全て通ることを確認。

## 3. `save_memo`のmode運用方針の変更

### 経緯

これまで`mode`(`"summary"`/`"raw"`)は「指定が無ければ`raw`」という固定ルールで、記録されるだけで実質的な使い道が無かった。隼と相談した結果、**「分類に迷ったら隼に聞く」**方式に変更する方針で合意。

### 対処

`core/brain.py`のSYSTEM_PROMPT、`### メモを作る(save_memo)`セクションの最終行を書き換えた。

**Before:**
```
- mode="summary"(要約)/"raw"(原文)。指定なければraw。titleは内容から適切に付ける。
```

**After:**
```
- mode="summary"(要約)/"raw"(原文)。隼が明示していればそれに従う。
- 指定が無く、要約か原文かで残る内容が変わりそうな場合は、保存前に「要約と原文、どちらで残しますか?」と確認する。
- 短い一言メモ等、どちらで残しても実質差が無い内容は、確認せずrawで保存してよい。
- titleは内容から適切に付ける。
```

`core/tools/memo.py`側(`save_memo`関数本体)は変更していない。「FALCONがいつ隼に確認を取るか」という判断ルールだけをSYSTEM_PROMPT側で変えた形。

### 備考

これはプロンプトの文言だけの変更のため、実際にFALCONが意図通り確認を挟むかどうかは、隼の手元での対話動作確認(`python core\brain.py`または`python main.py`)で見てもらう必要がある。

## 4. 豊田市問題(天気予報の区分をまたぐ地名への対応)

### 発端

`area_codes.json`の`aliases`は「1つの呼び名 → 1つの区分」という構造だったため、市内で西部・東部に分かれている豊田市を登録できずにいた(0717から持ち越し)。

### 現物確認(推測で断定しない、の実践)

豊田市がどのくらいの規模で、実際にどう区分されているのか、記憶に頼らず気象庁のデータを直接確認した。

1. **天気予報API(`230000.json`)** … 愛知県の天気区分は`230010`(西部)・`230020`(東部)の2つのみ
2. **地域マスターデータ(`area.json`)** … `class20s`(市区町村レベル)で「豊田」を検索したところ、以下が確認できた:
   ```
   2321101  豊田市西部 → 西三河北西部(230015) → 愛知県西部(230010)
   2321102  豊田市東部 → 西三河北東部(230021) → 愛知県東部(230020)
   ```

**豊田市は気象庁の公式区分として、天気予報の西部/東部という境界そのものをまたいでいる自治体**であることが確認できた(行政区分の話ではなく、天気予報の区分自体が割れている)。

### 方針決定

当初は「B: 西部/東部を別々に登録」「C: 複数区分を返せる構造にする」「D: 曖昧なら聞き返す」を提案したが、隼から「実際の民間天気サイトでは豊田市を東西に分けて表示していない」という実例(スクリーンショット)が示され、**「両方取得して、一致してれば1つに、割れてたら区分ごとに言う」**という設計で合意。データの取得・比較はPython側では行わず、生データだけ返してFALCON(Claude)側で言い分けさせる方針とした(`search_memos`のAND検索を必要以上に賢くしなかったのと同じ「賢さは呼ぶ側に任せる」の踏襲)。

### 実装

**`core/tools/area_codes.json`**: `aliases["豊田"]`を単一dictではなく、西部・東部それぞれの`{file, area, label}`を持つ**リスト**として登録。

```json
"豊田": [
  {"file": "230000", "area": "230010", "label": "西部"},
  {"file": "230000", "area": "230020", "label": "東部"}
]
```

**`core/tools/weather.py`**:
- `resolve_location` … 常にリストを返すよう変更(通常地名は要素数1、豊田だけ要素数2)
- `_fetch_forecast` … 1区分ぶんの取得処理を関数として切り出し(単一・複数どちらの場合も使い回すため)
- `get_weather` … 対象が複数ある場合は全区分を取得し、`{"location":.., "areas": [{"area_name":.., "forecast":[...]}, ...]}`の形で返す。単一の場合は今まで通り`{"location":.., "forecast":[...]}`のまま(既存の呼び出し側との互換性を維持)

**`core/brain.py`(SYSTEM_PROMPT)**: `get_weather`の結果に`areas`キーがある場合の言い分けルールを追記。

```
- 結果に"areas"キーがある場合(豊田市のように、天気予報の区分自体をまたぐ地名)、
  日付ごとに各区分の天気を見比べる。
  - 全区分で同じ天気なら、区分名を出さず1つの答えとして述べる。
  - 区分によって違う場合は、区分ごとに分けて述べる
    (例: 「豊田西部は晴れですが、豊田東部は雨です」)。
```

### 検証

隼の手元(`python -m core.tools.weather`)で実行し、以下を確認:
- 既存地点(名古屋・豊橋・浜松・熱海)は今まで通りの単一形式で正しく動作(回帰無し)
- 豊田は`areas`形式で西部・東部両方の予報が正しく返る

## 5. ★新ルール: 開発フローの見直し(今日から適用)★

### 経緯

これまでClaude(FALCON開発担当)が動作確認・テストの過程で、隼の実プロジェクトファイルのコピー(クローン)を直接編集し、「もう直しといたぜ」という形で報告していた。隼から「テスト目的以外は自分のファイルを直接編集せず、編集箇所を提示してほしい」という指摘があり、開発フローを変更した。

### 新しい方針

- **動作確認・テストのため**、Claude側の作業スペースでのファイル編集・実行は引き続き行う(現物確認の精神は変えない)
- 隼に見せる際は「もう直した」ではなく、**Before/After形式の編集指示(diff)** を提示し、隼自身が自分のファイルに反映する
- **例外: 引継書(Handoverファイル)** … これはClaude側が直接新規作成・編集してよい

この方針は、Claudeの記憶(memory)にルールとして追加済み。

## 6. 既知の問題(未対応・次回以降)

### `core/tools/calendar.py`が標準ライブラリの`calendar`モジュールと名前衝突する

`python core\tools\weather.py`のように、スクリプトを直接指定して実行すると、そのスクリプトのディレクトリ(`core/tools`)が`sys.path`の先頭に入るため、`import calendar`(標準ライブラリ)のつもりが自作の`core/tools/calendar.py`を掴んでしまい、`ModuleNotFoundError: No module named 'googleapiclient'`のようなエラーで落ちる。

`python -m core.tools.weather`(プロジェクトルートから`-m`付きで実行)なら回避できることは確認済み。ただし、`README.md`や`0716_setup.md`に書かれている動作確認手順(`python core\tools\weather.py`のような直接実行)は、この衝突を踏む可能性がある。

**対処は次回以降の課題**。案としては:
- `core/tools/calendar.py`をリネームする(例: `gcal.py`)
- ドキュメント側の実行コマンドを`python -m core.tools.weather`系に統一する

のどちらか、あるいは両方で対応することになりそう。
