## 1. `_test()`の整理(シナリオ選択式 + debugモード)

### 経緯

`core/brain.py`の`_test()`が、直近で触った機能(タスク管理)のデバッグ跡そのままで残っていた。docstringが「complete_task / delete_taskの確認用」なのに、実際には`add_task`と`list_tasks`しか呼んでおらず、**docstringと中身が食い違っている**状態だった(0722_01の「次回の起点」1番)。

### 対処

3つの改修を`core/brain.py`に加えた。

**① シナリオ辞書化** … `SCENARIOS`という辞書に「weather」「memo」「calendar」「task」ごとの会話文を並べ、`_test(scenario, debug)`が指定されたシナリオだけを流す形にした。機能を触るたびに`_test()`本体を書き換えなくて済む。

```python
SCENARIOS = {
    "weather": ["名古屋の天気は?", "じゃあ豊田はどうだ?"],
    "memo": ["「うどんも好き」って一言メモしといて", "さっき保存したうどんのメモ、探して"],
    "calendar": ["今週の予定を教えてくれ"],
    "task": ["りんごを買うのをタスクに追加して", "タスク一覧見せて",
             "さっき追加したタスク、完了にして", "完了したのも含めて一覧見せて"],
}
```

**② debugフラグ** … `ask_claude(client, user_message, debug: bool = False)`に変更し、`debug=True`の時だけ`[DEBUG] {type(message).__name__}: {message}`を表示する(0716-0717の教訓の技法を、コメントアウトではなく引数で呼び出せる形に整理)。デフォルト`False`なので`main.py`・`server.py`側は無改修で動く。

**③ コマンドライン引数化** … `argparse`で実行時にシナリオとdebugを選べるようにした。

```powershell
python core\brain.py                  # 省略時はtaskシナリオ
python core\brain.py weather          # 天気シナリオ
python core\brain.py memo --debug     # メモシナリオ + 生ログ表示
```

### ★後片付け機能(task/memoシナリオ)★

`task`・`memo`シナリオは実データ(`tasks.json`・`memos/`)に書き込むため、**実行前後の差分**を取り、そのテストで増えた分だけを削除する仕組みを追加した。

- 差分削除には`delete_task`・`list_tasks`・`list_memos`を**会話を介さず直接Pythonから呼ぶ**。SYSTEM_PROMPTの「`delete_task`は実行前に確認」はFALCON(LLM)が隼と会話する時の人格ルールであり、テストスクリプト自身の後片付けとは別物、という整理をした
- メモの削除は`os.remove()`を`_test()`内で直接使用。`memo.py`本体には`delete_memo`を追加していない(隼が読み返すファイルを消す機能を意図的にFALCON側に持たせない、という既存方針を維持するため)

### 検証

- `python core\brain.py task`を2回連続実行 → 両方とも新規追加分(ID4)がcleanupで正しく削除され、`tasks.json`にゴミが残らないことを確認
- ただし**Bを導入する前から存在していた重複タスク(ID3「りんごを買う」・完了済み)は差分の対象外**のため、まだ残っている。**要手動削除**(下記6参照)
- `weather`・`calendar`・`memo`シナリオも一通り動作確認済み(`--debug`あり/なし両方)

## 2. VPN導入(Tailscale)

### 方針

0721で保留にしていた「外出先からのアクセス」を、ポート開放ではなくTailscale(WireGuardベースのVPN)で実現する方針を採用。ポート開放不要、無料枠で個人利用に十分、という理由で選定。

### 手順

1. PC・iPhone双方に同一アカウントでTailscaleをインストール
2. `tailscale status`で両端末の疎通を確認(PC: `100.88.33.96` / iPhone: `100.121.215.31`)
3. `uvicorn server:app --host 0.0.0.0 --port 8000`でサーバー起動
4. iPhoneから`http://100.88.33.96:8000/`にアクセス

### ★発覚したバグ: モバイルSafariで画面が「灰色一色」に見える★

#### 現象と切り分け

`/docs`(FastAPI自動生成ドキュメント)は正常表示 → **サーバーへの到達自体は成功**。一方`/`(チャット画面)は画面いっぱいの濃い灰色一色に見え、実際は下にスクロールすると入力欄が存在した。

#### 原因

`static/index.html`の`body`に`height: 100vh`を指定していたが、**モバイルSafariは`100vh`をアドレスバー表示前提の高さとして計算する**という既知の挙動があり、実際に見えている範囲より`body`が長くなる。結果、下部の`#chat-form`(入力欄・送信ボタン)が可視領域からはみ出していた。PC上の検証(0721でRequestsやDevToolsを使った確認)ではこの問題は再現しない、モバイルSafari特有の癖。

#### 対処

`height: 100vh`の直後に`height: 100dvh`(動的ビューポート高さ)を追記し、対応ブラウザではそちらを優先させるフォールバック方式にした。

```css
body {
    ...
    height: 100vh;   /* 古いブラウザ向けのフォールバック */
    height: 100dvh;  /* モバイルSafariのアドレスバー分を正しく除いた高さ */
    display: flex;
    flex-direction: column;
}
```

### 検証

- 修正後、iPhone SafariでWi-Fi接続時に入力欄が画面内に収まることを確認
- **iPhoneのWi-Fiをオフにし、モバイル回線のみでの接続にも成功**(VPN導入の最終ゴール達成)

## 3. Wake-on-LAN: 検討の末に保留決定

### 構造的な制約

Magic Packetは対象PCと同じLAN内からのブロードキャストが前提。**隼のPCがスリープ/シャットダウン中は、そのPC自身のTailscaleもオフラインになる**ため、「外出先→Tailscale→スリープ中のPC」という直接の経路が成立しない。中継役として、PC以外に**常時稼働していてLAN内にMagic Packetを撒ける機器**(Tailscale対応ルーター、Raspberry Pi/NAS等)が別途必要。

### 現状確認

- 隼の自宅には、中継役に使えるPC以外の常時稼働機器が無い
- 現在使用中のルーター(コミュファ光 by ctc、型番F5648)について検索を試みたが、検索エンジン側のbot対策(DuckDuckGo/Bing/Google全てで人間確認を要求された)に阻まれ、仕様の詳細確認はできず
- 一般論として、ISPレンタルのホームゲートウェイはメーカー独自の閉じたファームウェアであることが大半で、OpenWrt等への換装やTailscale等のソフト導入は基本的に不可能と考えられる

### 決定

上記に加え、**0721時点で既に「PCは基本つけっぱなし運用(スリープ無効化)」の方針を決めている**ため、WoLが解決すべき課題は「停電・うっかりシャットダウン等の例外ケースの保険」に限られ、緊急度は高くないと判断。**追加ハードウェア購入(GL.iNet系トラベルルーター等、¥3,000前後)を要する話であり、今回は保留とする。**

再開する際の選択肢:
- **B: 中継用の安価なハードウェアを追加購入する**(GL.iNet系トラベルルーターが設定の手間が少なく有力)
- **C: 保留を継続する**(PCつけっぱなし運用が続く限り実害は小さい)

## メモ

- Tailscaleの通信は、コントロールプレーン(端末同士の鍵交換の仲介)をTailscale社が担うが、データプレーン(実際の会話内容)は端末同士が直接WireGuardで暗号化トンネルを張るため、Tailscale社を含む第三者に中身を見られる設計にはなっていない。隼のTailscaleアカウント自体のMFAは別途必須
- `100vh`と`100dvh`の違い(モバイルブラウザのアドレスバー分の扱い)は、今後iOS/Android向けのWeb UIを作る際に再発しうる典型パターンとして覚えておく価値がある
- ISPレンタルのホームゲートウェイ(ホームゲートウェイ型ルーター)は、型番で検索しても情報が出てきにくい・検索エンジンのbot対策に阻まれるケースがあることが今日分かった。次回同種の型番調査が必要になったら、検索より先にルーターの管理画面(`192.168.x.1`等)から直接確認する方が早い可能性がある
