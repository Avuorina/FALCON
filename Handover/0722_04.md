### 手順

1. Tailscale管理画面(https://login.tailscale.com/admin/dns )で「HTTPS Certificates」を有効化
2. PCのフルドメイン名を確認: `desktop-0cl2p6m.taila09f6b.ts.net`(管理画面の「Machine Details」→「Full domain」で確認)
3. 証明書を取得:
   ```powershell
   tailscale cert desktop-0cl2p6m.taila09f6b.ts.net
   ```
   → `desktop-0cl2p6m.taila09f6b.ts.net.crt` / `.key` の2ファイルがプロジェクト直下に生成される


## 2. ★Service Worker(オフライン対応)★

### なぜHTTPS化が先に必要だったか

Service Workerは、ブラウザの仕様上**HTTPSかlocalhostでしか登録できない**(「安全なコンテキスト」の制約)。今までのTailscale IP経由のHTTPアクセスでは、`navigator.serviceWorker.register()`自体が成立しなかった。上記1のHTTPS化で、この制約をクリアした。

### 設計方針

- **ページ本体(`/`へのナビゲーション)**: ネットワーク優先。失敗したらキャッシュ済みの`offline.html`を返す
- **`/static/`配下の静的ファイル**: ネットワーク優先、失敗時はキャッシュから返す(取得成功時はキャッシュも更新)
- **`/chat` `/history` `/system-stats`には一切関与しない** … これらのAPIエラーハンドリングは`index.html`側の既存の`try/catch`が担当済みのため、Service Worker側で二重に面倒を見ない

### ★scope(制御範囲)の注意点★

`sw.js`を素直に`/static/sw.js`に置くと、**Service Workerが制御できる範囲(scope)が`/static/`配下に限定され、肝心のページ本体(`/`)へのアクセスを横取りできない**。そのため`server.py`に`/sw.js`という専用エンドポイントを追加し、ルート直下から配信する形にした。

```python
@app.get("/sw.js")
async def service_worker():
    return FileResponse("static/sw.js", media_type="application/javascript")
```

### 実装したファイル

- **`static/offline.html`**(新規) … 「FALCON - OFFLINE」の案内ページ。既存UIと統一感のあるダークテーマ+オレンジアクセントで作成。「再試行」ボタンで`location.reload()`
- **`static/sw.js`**(新規) … install時に`offline.html`・manifest・アイコン類をプリキャッシュ。fetch時はナビゲーションとstaticで処理を分岐。`CACHE_NAME`にバージョン文字列(`falcon-cache-v1`)を持たせ、activate時に古いバージョンのキャッシュを削除する仕組みも入れた
- **`server.py`** … `/sw.js`エンドポイントを追加
- **`static/index.html`** … `window.load`時に`navigator.serviceWorker.register("/sw.js")`を追加

### ★重要な検証手順(初回インストールの罠)★

Service Workerは「一度正常にページを開いてインストールが完了したブラウザ」でしか機能しない。**コード反映後、一度もアクセスしたことが無いブラウザで、いきなりサーバーを止めて開くと、Service Workerが介入する前の状態なので、ブラウザ標準のエラー画面(`ERR_CONNECTION_REFUSED`)が出る**。これはバグではなく仕様通りの挙動。実際に検証中、PCのChromeで一度これを踏んで原因を切り分けた(一度正常アクセスしてから再度試したところ、想定通り`offline.html`が表示された)。

### 検証結果

- サーバー稼働中に一度アクセス・チャット動作確認 → Service Worker登録・プリキャッシュ完了
- サーバー停止中にリロード → 真っ白画面ではなく`offline.html`(「FALCON - OFFLINE」案内)が表示されることを確認
- サーバー再起動後、「再試行」ボタンで通常のチャット画面に復帰することを確認

## 3. Google OAuthの「ウェブアプリケーション」種別化 → 保留に決定

### 確認した内容

現状の「デスクトップアプリケーション」種別・`InstalledAppFlow`ベースの認証は、**隼が自分のPC上でFALCONを動かし続ける限り実害が無い**設計であることを再確認した。

- 認証フロー(`run_local_server`)はサーバーを動かしてるPC自身でブラウザを開いて完結する
- 一度`google_token.json`が保存されれば、以降は`refresh_token`でブラウザを開かずに自動更新される

この項目がなぜ引継書のToDoに入っていたか、隼に確認したところ**具体的な動機は覚えていない**とのことだった。無理に推測で対応するより、保留にして次の再浮上条件を明記しておく方が安全と判断した。

### ★再浮上させる条件★(これが起きたら本気で検討する)

- **A: リフレッシュトークンが数日で失効し、カレンダー機能が認証エラーを吐くようになった** … Googleの仕様で、OAuth同意画面の「公開ステータス」が「テスト」のままだとリフレッシュトークンが7日で失効する。この場合の正しい対処は「ウェブアプリケーション」種別への変更ではなく、**OAuth同意画面の公開ステータスを「本番」に切り替えること**
- **B: 外出先(スマホ)からFALCON経由で使用中に、初回認証(ブラウザでの許可)をやり直す必要が生じた** … PCの前にいないと今の仕組みでは再認証できないため、この不便が実際に起きたら、サーバー側でOAuthリダイレクトを受け取る「ウェブアプリケーション」方式への作り直しを検討する価値が出る

どちらも現時点では発生していないため、今回は対応を見送った。

## 7. 既知の問題・積み残し

### アイコンとUIの配色が一致していない(0723_01から持ち越し)
PWAアイコン(仮)は旧配色(青系)のまま、UIは新配色(オレンジ系)。隼が本番アイコンを用意する際の判断次第。

### 背景の脳ワイヤーフレーム画像が未実装(0723_01から持ち越し)
`#brain-visual`というフックは用意済み。画像ができたらCSSに`background-image`を1行足すだけで差し込める。

### NETバーの基準値(2MB/秒)は暫定(0723_01から持ち越し)
体感に合わなければ`core/tools/system_stats.py`の`_NET_REFERENCE_BYTES_PER_SEC`を調整する。

### Wake-on-LAN(意図的に保留中)
追加ハードウェア無しでは実現困難と判断し保留。

### Google OAuthのウェブアプリ種別化(意図的に保留中、今回明確化)
上記3の再浮上条件が発生するまでは対応不要。

### Service Workerのキャッシュバージョン管理を忘れずに
`static/`配下の静的ファイル(アイコン・manifest等)を今後更新した際は、`static/sw.js`の`CACHE_NAME`(`falcon-cache-v1`)を必ず変更すること。変えないと古いキャッシュが残り続け、更新が反映されない。

## メモ

- Service Workerの「安全なコンテキスト」制約(HTTPS/localhost必須)は、LAN内アプリやセルフホスト用途で見落としやすい典型的な罠。個人用サーバーをTailscale等のVPN経由でIPアドレスのままHTTPS無しで使ってると、PWAの一部機能(Service Worker、一部のセンサーAPI等)が理由も分からず動かない、ということが起こりうる
- TailscaleのHTTPS証明書機能は、自己署名証明書を自分で管理する手間なく、正式な(ブラウザに警告を出させない)証明書を無料で発行してくれる。セルフホスト個人サービスをTailscale経由で公開する際の定番の組み合わせと言える
- 「なぜこのToDoを積んだか動機を忘れる」ことは、開発が長期化すると普通に起こる。無理に推測で実装するより、「保留にして、再浮上条件を明文化しておく」方が、後から見て安全なことが今回分かった
