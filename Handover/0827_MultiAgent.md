## 今回のお題

全機能に人格AIを立てるのではなく、**実務ツールと人格AIを分けて**、職業単位で担当を切るマルチエージェント構成をどう作るか。

---

## 1. 決定事項

### 担当の切り方
- 担当は「職業(仕事の種類)」で切る。
- **全機能に人格AIを立てない。「実務ツール」と「人格AI」を分けて考える。**
  - **実務ツール**(天気・メモ・スケジュール・タスク・電源プラン操作)= 状態を持たず一回で完結する処理。専属の人格を割り当てず、どの人格からも呼べる共有ツールとして運用。
  - **人格AI**(例: 日常AI、攻略AI)= 喋り方や専門知識が異なる、実体として別のAIセッション。日常AIが既定人格、攻略AIは専門人格の例(まだ仮の例)。

### ツールをどの人格に持たせるか
- 判断基準は「処理コスト」ではなく **「その人格の会話に自然に出てくる作業か」** という意味的な適合性。
- 参考: 組み込みツール93個→自作5個で `cache_creation_input_tokens` が 26,039→1,784 に減少した実績(0717)。コスト自体は今回の規模(十数個)では問題にならないと判断。

### 人格×ツール対応表(チェックリスト)
- 固定で決め切らず、後から切替可能にする。
- 使用感: AI応答 → 隼がチェックを入れる → 隼が発言 → **その時点の対応表でツール構成が更新されて応答**。チェックを入れた瞬間ではなく、次の発言のタイミングで確定する。
- チェックリストAPIの形は **「選択中の人格1人分だけ返す」方式**に決定(全人格まとめて返すマトリクス方式ではない)。Dashboard は今選ばれているタブの人格分だけ都度取得する。人格が増えても1回のやり取りの重さが変わらない利点がある。

### チェックリストUIの置き場所
- **FALCON-Dashboard**(Windows専用デスクトップアプリ)に新設する。
- PWA は「ネイティブスマホアプリを作れないための次善策」であり、PC/スマホの体験を意図して統一したものではないため、**PCでは制約のない Dashboard を主インターフェースとする**方針。
- 設定の実体はサーバー側(`server.py`)に一元管理。Dashboard は HTTPS(Tailscale)経由の既存接続を使う読み書きクライアント。
- PWA側への展開は優先度を下げて保留。
- Dashboard の既存タブ構成(チャット/Minecraftログ/タスク一覧/カレンダー、後2つは実装中で "準備中" 表示)に「ツール設定」タブを追加する形にする。

### 配色方針
- ベースは `App.xaml` の既存トークン(`BgBrush` #0a0c10、`AccentBrush` #ff8a3d 等)を維持。
- 人格ごとに、オレンジ基調のまま**色相だけ少しずつずらした専用アクセント色**を与える。
  - 既存の `AccentBrush` はタブ下線・接続ステータスなど「アプリ共通の地の色」として現状維持。
  - 人格ごとの色は `AccentBrush_日常` `AccentBrush_攻略` のような別トークンとして追加し、チャットの発言プレフィックス(「攻略AI>」等)とヘッダーの人格バッジにのみ使う。
  - 色の作り方は感覚で選ばず、基準色(#ff8a3d)から**色相を一定角度ずつ機械的にずらす**ルールにする案。彩度・明度は基準に揃え、色相のみ動かす。人格が増えても配色に毎回悩まずに済む。
  - 正確な角度・最終的な見た目の微調整は Claude Design 上で実物を並べながら詰める。

## 2. フェーズ2(今回のスコープ外、将来やりたい)

隼が Design で作ったモックアップ(CORE / ORACLE / FORGE / ECHO という仮称の人格構成)をきっかけに浮上した話。**名前は仮置き**で、深く捉えないこと。中身だけ記録しておく。

- **FORGE(仮称、開発・エンジニアリング担当)**: コードを書く/直す専門人格。天気やメモと違い、コード変更という強い書き込み権限を持つため、実務ツールと同列には扱えない。着手時は 0720 の教訓(`enable_file_checkpointing`、破壊的操作の事前確認、権限の意図的な開放)を踏まえて別枠で安全設計をやり直す必要がある。
- **並行マルチエージェント**(CORE→ORACLE/FORGE 等への委任、ACTIVE/IDLE/BUSY 表示): 窓口(CORE)が調査や実装を ORACLE/FORGE に投げて裏で並行実行させ、隼は CORE と会話を続けられる構成。パターン自体は妥当(いわゆる supervisor/orchestrator 構成)だが、FALCON 固有の理由で時期尚早と判断:
  - FALCON は API 従量課金ではなく Claude サブスクの5時間枠を消費する方式。並行エージェントはこの共有の有限枠を同時に食う。
  - 今の FALCON はまだ「窓口が1人格を選んで応答する」の単純な形すら未実装。土台を検証する前に多段構成にすると、セッション寿命まわりのバグ(0716/0717 で苦労した `async with` のライフサイクル問題)がエージェント数分に増える。
  - FORGE と相性が良い(FORGE が裏でコードを書いてる間も CORE と雑談できる、が並行処理の一番わかりやすい使い道)ため、この2つはセットでフェーズ2として扱う。

## 3. 未決定・持ち越し事項

- 攻略AI(例)にスケジュール・タスクを含めるか → 対応表のデフォルト値として仮決めし、運用しながら調整。
- 窓口AIが天気ツールを直接持つべきか。
- `ClaudeSDKClient` はセッションを維持したまま内部のツール構成だけ差し替え可能か → 実装時に SDK 現物確認が必要。もし不可能でも会話ログを新セッションに引き継げば継続性は保てる。
- PWA側のチェックリスト対応(保留)。
- Dashboard の「ツール設定」タブで、人格を手動固定する切替(自動振り分けが外れたときの逃げ道)を設けるかどうか。
- 人格ごとのアクセント色相の具体的な角度・最終値(Design で詰める)。

## 5. 実装前の確認事項(本セッション 2026/09/10 で判明)

「設定の実体は `server.py` に一元管理」を前提にする前に、`server.py` の現状を GitHub `main` で確認したところ、退行が1件見つかった。

- 2026/07/25 のコミット「♻️ server.pyをFalconSession共有に置き換え」で `server.py` は `core/session.py` の `FalconSession` を使う形にリファクタされていた。
- しかし同日の `Merge branch 'main'` + 翌 07/26 の「✨ server.pyにPOST /shutdownを追加」で、`server.py` が **`falcon_client` + `chat_history` の旧設計に戻ったまま** `/shutdown` が載った(マージ衝突を旧版側に倒した跡)。
- 現在の `main` の `server.py` に `session` は存在しないが、`run.py` は今も `from server import app, session` を実行する → **`python run.py` は ImportError で落ちる**。Discord Bot 経路は動かない状態。
- `core/session.py` / `discord_bot.py` / `run.py` 自体は無事コミットされている。「配線の片端(`server.py`)だけマージで剥がれた」形。

→ マルチエージェントの「ツール設定 API」を `server.py` に生やす前に、まず `server.py` の `FalconSession` 化を復活させて `run.py` が通る状態に戻すのが先。復活後の形は `0725_DSbot.md` の設計(`lifespan` が `session.start()`/`session.stop()`、`/chat` → `session.ask("隼", ...)`、`/history` → `session.history`、`falcon_client`/`chat_history` は削除)を踏襲し、後から入った `/shutdown` `/minecraft/*` `/system-stats` `/sw.js` は残す。
